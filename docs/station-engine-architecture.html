Architecture

Process

One process, one port, no window

The engine is an ASP.NET Core application with no UI project anywhere in the tree. It is started with a port and it binds loopback:

StationEngine --port 6060

That single port carries both halves of the station protocol: ordinary HTTP for control and configuration, and one WebSocket at /ws for everything that streams. A client discovers what it is talking to at /api/station/version. Four other flags exist — --bind lan, two LAN HTTPS ports, and --native-audio-output — and the parser rejects contradictory combinations up front rather than half-opening a listener.

Around that core sit three more listeners that are not the station protocol at all: a CAT server, a TCI server sharing Kestrel, and an optional serial CAT port. They exist so that logging software, contest loggers and third-party SDR applications can drive the same radio without going through the Zeus client.

Assemblies

Eleven projects, and one of them is the engine

The dependency graph is unusually flat, and unusually lopsided. Station.Engine.Hosting is 86,000 lines — two thirds of all the C# in the repository — against 656 lines in the executable that starts it. The entry point is a launcher; the hosting library is the product.

The shape underneath is disciplined, though. Zeus.Contracts is a leaf: it references nothing, and the two transports and the DSP layer all depend on it. That is what lets a protocol change be a change to one wire type rather than a change everywhere.

Transport

Two protocols with incompatible ideas about sockets

Both HPSDR protocols run over raw UDP to a radio discovered by broadcast on port 1024. That is where the similarity ends, and the difference is structural rather than cosmetic.

Protocol 1 multiplexes everything through one socket. IQ, microphone audio, PTT state and control all share the same datagram stream, distinguished by endpoint numbers inside the payload — EP2 outbound, EP6 inbound. Protocol 2 gives each function its own UDP port, so a receiver, the wideband ADC snapshot, the transmit IQ and the command channel are separate sockets that can be reasoned about, rate-measured and stalled independently.

That is why the engine carries two full client implementations, 7,500 and 6,900 lines, rather than one with a switch.

Board identity matters more than the protocol number. The engine carries a capabilities table keyed on eight board kinds, because what a radio can do — balanced XLR input, line-in gain, bias on the microphone jack, an internal PureSignal coupler — varies inside a single protocol. The transmit-audio source enum has four values, and three of them are only offered on hardware that physically has the jack.

Receive

From antenna to browser at 48 kHz

The receive path is the engine's steady state, and every stage in it is fixed-rate. The radio decimates to one of four IQ rates; WDSP consumes 512-sample blocks and always emits 48 kHz audio; the analyser runs a 16,384-point FFT at 30 frames per second regardless of what the panadapter is showing.

Eleven demodulation modes are exposed, and one of them is a lie in a useful way. FreeDV is not a WDSP mode at all: at the DSP layer it runs as USB, with the Codec2 modem inserted into the audio path through the same plugin seam that carries everything else. The enum comment says never to reorder the values — they are persisted by ordinal.

Transmit

The path that can burn something

Transmit runs the same machinery backwards, with one addition that receive has no equivalent for: a policy module that can refuse. TxService is the only executor of DSP and radio edges, but it evaluates immutable snapshots handed to it by an engine-owned safety module, and a revision token is checked twice — once at the shared egress, and again immediately before each transport send. Admission by policy alone never opens the gate; it opens only after the matching wire transition has actually succeeded.

Surface

Station protocol: 199 routes and 35 frame types

The split between HTTP and WebSocket is not arbitrary. Anything with a request and a reply is a route; anything continuous is a frame with a one-byte type. The type byte is allocated in a deliberate pattern — 0x0x for the core receive stream, 0x1x for server-to-client telemetry, 0x2x for client-to-server uplink and control, 0x3x for feature streams added later.

The streaming hub carries one design decision worth stealing. Each client has a bounded backlog of 48 entries, and when it overflows the queue does not drop the oldest — it drops by kind. Display snapshots and meter telemetry are replaceable and go first; PCM is not and is protected. The comment records why the number is 48 and not 16: at 16 entries the queue held only about 350 ms of audio, and a rich 3D draw or a burst of VFO updates could keep a WebView from draining its socket for long enough to cause audible dropouts.

Security posture is loopback-first. The engine binds 127.0.0.1 unless explicitly told otherwise, an optional access token gates every request, and plugin installation and removal are rejected with a 403 from any non-loopback address — regardless of token. LAN exposure requires both a flag and a generated certificate, and the argument parser refuses the combinations that would half-open it.

State

Everything the operator changed, in two files

There is no configuration file. Around thirty typed stores — band memories, filter presets, antenna settings, CW keyer, PureSignal timing, audio devices, layouts, themes — all persist through LiteDB into station-engine.db under the platform application-data directory. Forty-four source files touch the database layer.

The QSO logbook is deliberately separate, in zeus-logbook.db. The reason is a lifecycle difference rather than a schema one: preferences fork per profile and are treated as disposable, and a developer resetting to a clean state should not lose their log alongside them. There is exactly one logbook per data directory, and it never forks.

Extension

Subsystems, plugins, and the native floor

Eight subsystems live in their own directories inside the hosting library, and they are the clearest signal of what this engine is actually for. CAT (10 files) and TCI (14) exist to let other software drive the radio. A receive-side CW decoder (7 files) runs when a client asks for it and unwinds on disconnect. TDoA (10 files) — geodesy, a pair analyser, a solver — locates a transmitter by comparing arrival times across receivers. HF auto-tuner control, KiwiSDR integration, and support for an SPE Expert 1.5K Taurus amplifier round it out.

Plugins

The plugin host scans a root directory at startup and catalogues what it finds without loading assemblies. Activation is wrapped in try/catch with a per-call timeout, so a plugin that hangs in InitializeAsync fails alone. Manifests are validated against a declared ABI version, and the host scans for VST and Audio Unit components separately. Plugin identifiers are ordered in the audio chain and that order is itself broadcast to clients as a frame type.

Native

Underneath the C# sits 23 MB of vendored C, and the choices there are documented as compromises. WDSP — Warren Pratt's DSP engine, loaded by P/Invoke — is vendored at upstream 1.29 with a portability shim, because the reference implementation's own tree is MSVC-only and unsuitable as an upstream. Two noise-reduction paths are build flags with no-op stubs when disabled. RNNoise ships without a baked-in model, so that stage is inert until an operator installs weights. Prebuilt binaries are checked in for four runtime identifiers: win-x64, win-arm64, linux-arm64 and osx-arm64.

Provenance

An independent implementation with a paper trail

Every substantial source file opens with a 40-line header, and it is not boilerplate. The engine states plainly that it is an independent .NET reimplementation and not a fork, then names the projects whose behaviour informed it — Thetis for Protocol 1 and 2 framing, WDSP integration and transmit behaviour; pihpsdr and DeskHPSDR for Protocol 2, PureSignal and Saturn-class specifics — and credits fifteen individual contributors by name and callsign.

The licensing follows the same care, and it is layered rather than uniform. Most first-party code is GPL-2.0-or-later. A distribution without the ASIO host bridge is conveyed under GPL-3.0-or-later; a Windows distribution containing the Steinberg SDK-derived bridge is GPL-3.0-only, because that SDK's version 3 option carries no "or later" grant. The amplifier support under SpeTaurus/ is GPL-3.0-or-later on its own terms. Four separate documents carry the detail, one of them 23 KB of per-component attribution.

This repository is published as the complete corresponding source for the engine binary shipped with Zeus SDR, and each release tag matches the engine in the corresponding Zeus release.
