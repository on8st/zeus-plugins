Wavelog Logger

A station-engine plugin that pushes every logged QSO to a Wavelog instance. Its entire shape is forced by one fact about the framework — and the design is mostly about refusing to let the network anywhere near the operator.

Plugin id on8st.wavelog Target wavelog.on8st.be SSOT source/design.md

Thesis The framework has no “QSO logged” event, so the only seam is ILogbookPluginV2 — and that seam is the storage port, not the experience. The plugin becomes the store; the client keeps browsing, sorting and editing. Its first duty is therefore being a good store, and pushing to Wavelog is a side effect that must never be able to fail a QSO.
§1

The write path

What you are actually replacing

ILogbookPluginV2 is a data-access contract: create, update, delete, GetEntriesAsync(skip, take), fetch by id, worked summaries, ADIF import and export. Browsing, sorting, searching, the edit dialogs and the QSL workflow all live in Zeus Link and call through it. You implement roughly fourteen methods over a store and rebuild nothing the operator sees.

Three details make the job smaller than it first looks. There is no search, sort or filter parameter anywhere — the client does that itself over what it has pulled, so your store needs bulk reads but no query language. AdifFields is a dictionary on both the new entry and the snapshot, so arbitrary ADIF fields round-trip intact. And ADIF export is in the contract regardless, so the mapper is not Wavelog-specific cost — one piece of work, two consumers.

What you cannot lean on is the built-in store: no handle exists on IPluginContext, and it lives in the closed client. Nor should you open zeus-logbook.db directly — undocumented schema, and the client may hold it open.

Why the network stays downstream

The obvious implementation — CreateAsync posts to Wavelog and returns — is wrong, and it fails at exactly the worst moment. Wavelog runs in Docker on the multihost behind Caddy. If that box is rebooting mid-contest, logging a contact must still work.

So the network is strictly downstream of the operator. The call returns as soon as the QSO is durable locally.

One alternative, explicitly rejected. Knowing the seam is storage, Wavelog could be the store — GetEntriesAsync querying it on every browse. Cloudlog-family APIs are write-oriented, that method sits on the browsing path, and it would put the network between the operator and their own log: the exact failure this section exists to prevent.
§2

The outbox is the interesting part

The HTTP call is the boring half — a POST and a status code. The queue in front of it is where correctness actually lives: what happens when the process dies mid-flight, when the key is wrong, when the instance returns HTML instead of JSON.

§3

Shape, and where the tests can reach

Ports and adapters, arranged so the parts carrying the risk need no infrastructure to test.

Dependencies stay deliberately few. The host's load context resolves Zeus.Plugins.Contracts, Microsoft.*, System.* and netstandard from the default context, but everything else ships in the plugin's own directory — so System.Net.Http is preferred over any third-party client.

NetworkAccess is declared honestly even though it is not enforced at runtime — nothing stops loaded .NET code opening a socket. The manifest is what the operator reads, not a sandbox.

The API key never appears in the manifest. It lives in ctx.Settings, which is plugin-scoped and host-persisted, and the config GET never returns it.

§5

TDD order

Start where the risk is, not where the interfaces are. Each group is red first.

  1. AdifMapperTests — pure, table-driven Frequency to MHz at six decimals · band derivation · mode and submode split · UTC handling · RST defaults · optional fields omitted rather than emitted empty · <eor> · awkward characters in a comment · callsign casing.
  2. OutboxTests — the ones that catch real failures Enqueue survives a restart · a lease is exclusive · ack removes · nack reschedules with backoff · an item in flight when the process dies is redelivered, not lost · poison items dead-letter after N attempts.
  3. RetryPolicyTests — the distinction that matters 401/403 dead-letters immediately; 5xx and timeouts back off; 400 dead-letters with the response body kept.
  4. WavelogClientTests — stub HttpMessageHandler Correct URL and body · a non-JSON response is a failure, not a success · status surfaced.
  5. PumpTests — fake clock, fake transport Drains in order · backs off while the instance is down · recovers and catches up · never loses an item.
  6. LogbookFacadeTests — these two encode the design CreateAsync returns without touching the transport. CreateAsync still succeeds when the transport throws.
  7. SyncTests — the pull half, and the trap An imported QSO does not enter the outbox · the cursor advances to the returned lastfetchedid and never regresses · a confirmation sweep updates QSL fields without duplicating · full resync is idempotent, so a second run inserts nothing · full resync never deletes · two resyncs cannot run at once · a QSO in an unselected profile is not imported, and status says which profiles are synced.
  8. ConfigEndpointTests GET never echoes the key · PUT validates the URL.
Integration tests come last and stay opt-in. Real LiteDB and a real wavelog.on8st.be belong in a separate project, so the default run needs no network, no database and no radio.
§6

Wavelog's API — verified against source

Read from wavelog/wavelog at af32561 (2026-08-09), cloned to ~/Repos/on8st/wavelog. Not from memory.

The duplicate key — this closes the retry question

POST /index.php/api/qso
{ "key": …, "station_profile_id": …, "type": "adif", "string": "<record>" }

→ import_bulk(..., $skipDuplicate = true, ...) matches on:
  COL_CALL = ?
  AND DATE_FORMAT(COL_TIME_ON,'%Y-%m-%d %H:%i') = DATE_FORMAT(?,'%Y-%m-%d %H:%i')
  AND COL_BAND = ? AND COL_MODE = ? AND station_id = ?

Callsign + time to the minute + band + mode + station. So at-least-once is safe — a timed-out POST that did land is silently skipped on retry, and no client-side idempotency key is needed. Two caveats follow from the same query: send the same time_on you stored (12:00:59 re-sent as 12:01:00 is a new QSO), and mode must match exactly, or you get duplicates rather than collisions.

Read — and it is source-blind

POST /index.php/api/get_contacts_adif
{ "key": …, "station_id": … | [ … ], "fetchfromid": 0,
  "limit": 500, "output_format": "adif" | "json", "fields": [ … ] }

→ { status, lastfetchedid, exported_qsos, adif }

Adif_data::export_past_id_chunked
  WHERE station_id IN (?) AND COL_PRIMARY_KEY > ?
  ORDER BY COL_PRIMARY_KEY ASC LIMIT ? OFFSET ?

No filter on origin. A QSO entered in Wavelog's web UI, uploaded by WSJT-X, bulk-imported from another logger or posted by any other client gets an auto-increment key above the cursor and returns on the next poll. Wavelog is the meeting point; Zeus is one writer among several.

logbook_check_callsign and logbook_check_grid also exist — server-side worked-before checks, so GetWorkedSummaryAsync could see contacts logged by other apps without importing them.

§7

Synchronisation

COL_PRIMARY_KEY is AUTO_INCREMENT, so the cursor follows insertion order, not QSO date. A bulk import of 2015 contacts made today lands above the cursor and is picked up. A timestamp cursor keyed on QSO date would have missed that import silently — which is the reason to prefer the primary key.

But an UPDATE does not change the key. A row modified after the cursor has passed is invisible to the incremental pull forever — and that hits the one reverse flow that matters, because LoTW and eQSL confirmations arrive as updates to existing rows.

Station profiles — the gap that is silent

The query filters station_id IN (?). QSOs imported under a different station profile are invisible to the sync permanently, not late — import an old log under an "Old QTH" profile while Zeus syncs "Home" and you get no error and no contacts.

The API solves it if you ask: station_id accepts an array, station_info lists every profile the key can reach, and an unreachable id fails loudly. So configuration must not take a single profile id — call station_info, show them all, let the operator tick which to sync, default to all, and have status name them. Note the asymmetry it makes explicit: you pull from many profiles and push to one.

Full resync — the repair button

Incremental is the normal path; the config UI also offers sync full database for when a gap has appeared — a crash mid-lease, a spell of misconfiguration, a restored backup. It is cheap because both sides already dedupe: it is the incremental loop with the cursor set to zero.

  • Both directions, one action. A gap can be on either side and the operator cannot know which.
  • Insert only, never delete. "Full sync" must not be read as "make identical".
  • Dry run first — "12 in Wavelog not here, 3 here not in Wavelog — apply?"
  • Resumable and single-flight.
  • It repairs absence, not divergence — it cannot see a record present on both sides with different content.
The trap: imported QSOs must bypass the outbox. Import is a different write path from CreateAsync. Without that, a full resync enqueues your entire log for push-back — thousands of no-op inserts hammering Wavelog to achieve nothing, while the outbox churns and status reports a backlog that never means anything. It is the single most important test in §5.
§8

Features — one plugin, opt-in

Wavelog is more than a log backend. One plugin, one API key, one config panel with toggles — rather than three plugins each holding the same credential. Each feature independently testable and disableable, which matters because one of them touches a UI path.

FeatureEndpointDefault
Log sync — push, pull, confirmations, resyncqso · get_contacts_adifon
Live rig stateradiooff
Worked-before enrichmentlogbook_check_callsignoff
New-grid alertslogbook_check_gridoff

Live rig state

POST /api/radio takes radio, frequency, mode, power, timestamp, plus uplink_freq/uplink_mode for satellite work. Zeus already has all of it and already exposes it — ctx.Radio with FrequencyChanged, ModeChanged, MoxChanged. A few lines of event handler make Wavelog's QSO entry form auto-fill your current QRG and mode and show the station live, from any browser including a phone.

Needs ReadRadioState and a write-permission API key — read-only keys are rejected. Completely independent of the logging path, which is why it is cheap.

Worked-before, and why it stays off by default

logbook_check_callsign keys on logbook_public_slug, not station_id — a different addressing scheme, so its own config field. The appeal is real: GetWorkedSummaryAsync answered by Wavelog sees contacts logged by every app. The catch is that it puts the network on a UI path, the exact opposite of §1. So local answer first, Wavelog as enrichment with a short timeout and a cache — never the blocking source.

What Wavelog already does, so Zeus need not

The strongest argument for this approach is not any single integration — it is the surface you inherit: confirmation pipelines (LoTW, eQSL, Clublog, QRZ, HRDLog, WebADIF, DCL), awards and analytics (gridmap, distance records, zone checker, statistics, timeline), QSL management (cards, printing, labels, OQRS), contest (logging, Cabrillo export, FLE) and satellite (Hamsat, sat timers, AMSAT status).

Deliberately not integrated

Dxcluster and Bandmap overlap what Zeus already has — its own SpotManager, the TCI spot feed and a SpotList frame type. Two spot sources competing for one screen is worse than one.

§9

Phases

Phase 1 — log and radio

The product. Everything an operator needs, configured over HTTP.

MilestoneContains
1a — storeILogbookPluginV2 over a local store · ADIF mapper · export and import
1b — pushoutbox · pump · retry policy · POST /api/qso
1c — pullincremental fetchfromid loop · confirmation sweep · profile selection
1d — repairfull resync, dry run first
1e — radiolive rig state to POST /api/radio

1a is shippable on its own — a working logbook that syncs nothing. Each milestone after it adds one loop, and each is independently revertible by a config toggle.

The gate — phase 1 must be proven before phase 2 starts

Phase 1 rests on assumptions the engine repository cannot verify (§12): whether Zeus Link calls ILogbookPluginV2 at all, when, whether a fallback to the built-in exists, and what happens on uninstall. None of it is knowable from source — it has to be established by running it. And phase 2 adds network to a UI path, so doing that on top of an unproven store compounds two risks that are far easier to diagnose apart.

Phase 2 does not start until all of these hold:

  • Zeus Link actually uses the plugin as its logbook — the biggest unknown, unanswerable any other way
  • Browsing, sorting, searching, editing and deleting all work through it, client UI unchanged
  • Performance is acceptable at real log size — GetEntriesAsync is on the browsing path and the client appears to filter client-side, so it may pull more than a page
  • a QSO logged in Zeus appears in Wavelog within the poll interval
  • a QSO logged elsewhere — web UI, WSJT-X, another logger — appears in Zeus
  • a LoTW confirmation reaches Zeus after the daily sweep
  • full resync dry-run reports zero drift after a week of normal use
  • uninstall and reinstall leaves the log intact and exportable

Run it on a scratch profile first, then the real log, and let it soak under ordinary operating before calling it proven. The dry-run resync is the cheap weekly check: if it keeps reporting nothing to do, the loops are working.

Phase 2 — enrichment

logbook_check_callsign and the grid checks. Separated because it has a different risk profile — the only part that puts the network in front of the operator, so it needs a cache, a timeout, and a local fallback exercised by tests rather than assumed.

Phase 3 — the panel

Blocked on external information, not on us — the UI contract belongs to Zeus Link and is not in the engine repository (§11). Phase 3 starts when upstream answers or a registry plugin publishes its source. Until then phases 1 and 2 are fully usable over the endpoints in §4.

Sequenced this way, the only phase that can stall is the one that adds no capability.

§10

Open before the first test

Per-entry upload state

The contract already carries UpdateQrzUploadStatusAsync, so there is precedent for per-QSO upload status. Mirror it: store wavelogUploadedAt and a failure reason, so status can report honestly and retry has something to work from.

§11

The panel comes last, and why

ui.modules and panel slots are consumed by Zeus Link, which is proprietary and not in the engine repository. Its shipped bundle carries an explicit “may not be … decompiled, disassembled, or reverse engineered” clause, so it is not a legitimate source for reconstructing the contract.

The layout does suggest one thing legitimately: the bundle ships wwwroot/zeus-sdk/react.js and react-jsx-runtime.js as separate importable modules — what you do when third-party modules are meant to import your framework rather than bundle their own.

To learn it properly: ask upstream, where issues are enabled and the one prior issue was handled, or find a registry plugin that publishes its source. Until then the plugin is fully usable without a panel, configured over the endpoints in §4 — which is also why deferring it costs nothing.

§12

Risks worth stating up front

You are replacing the store, not the logbook UI. The operator's experience is unaffected; what moves is the data — your QSOs live in this plugin's storage. Before running it against a real log, confirm ADIF export works and that uninstalling leaves the data recoverable — write the export test before the import path, not after.
The engine cannot verify the consumer. ILogbookPlugin is never called anywhere in the engine repository; Zeus Link calls it. When it is called, whether a fallback to the built-in exists, what happens if the plugin is uninstalled with entries in it — none of that is knowable from the GPL source. Establish it empirically on a scratch profile before trusting it with a real log.
